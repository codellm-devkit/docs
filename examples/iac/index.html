IaC examples

These examples analyze the Quarkus Coffee Shop Helm chart, the recurring sample across the IaC documentation. The chart lives in the quarkuscoffeeshop-helm repository under charts/quarkuscoffeeshop-charts. The page groups the examples by task: set up the analysis, inventory the files, inspect the templates, inspect the renders, and publish the graph. Each example shows behavior that the backend test suite asserts, unless a comment says that a value is illustrative.

No SDK facade

CLDK has no CLDK.iac() facade. Every example on this page is a caniac command, a jq filter over analysis.json, or a Cypher query. The codeanalyzer-iac backend page covers install and the full CLI reference. Install caniac and jq before you start.

Set up the analysis

Section titled “Set up the analysis”

Clone the sample. Then move to the pinned commit.

Every command uses --app-name quarkuscoffeeshop. That name identifies the application, so every id starts with can://iac/quarkuscoffeeshop or can://artifact/quarkuscoffeeshop/. The Helm release name is coffee. The chart helpers put the release name into resource names, for example coffee-quarkuscoffeeshop-charts. The application name and the release name are two different things.

Save this configuration as .codeanalyzer-iac.yaml in the repository root. It declares two render profiles for the chart. Both profiles use the release name coffee and the namespace quarkuscoffeeshop-demo. The second profile disables the service account.

Each set entry is a string, as with helm --set-string, so "false" is a non-empty true value and only "" is false.

Write the analysis output to a directory outside the clone. The backend records every file under the workspace root. It skips the .git, .hg, and .svn directories. If the output directory is inside the clone, the next run records the output file as an artifact.

Analyze the source at level 1

Section titled “Analyze the source at level 1”

Level 1 reads the files and records source facts. It resolves nothing and renders nothing.

Render at level 3

Section titled “Render at level 3”

Level 3 reads the configuration file and renders each profile with the embedded Helm SDK. Pass --config with the path of the configuration file, relative to the repository root. Every later example reads this level 3 document.

Analysis levels for this chart

Section titled “Analysis levels for this chart”

This scale is not the SDK scale

caniac takes --analysis-level 1, 2, or 3, and rejects 4. The language backends take levels 1 to 4. The two scales do not line up. The backend page has the general table.

The levels are additive. Every fact from a lower level is present, unchanged, at each higher level. This table shows what each level adds for this chart.

LevelWhat this chart gets
1 (default)15 artifacts, 8 with an iac facet and 7 raw. 6 named templates, all in _helpers.tpl. 9 include calls with no target_id. 16 resource templates. One config_key for each mapping key and sequence index in values.yaml, parent keys included. The chart renders map is {}.
2iac_part_of_chart edges from the 5 template files to the chart. A target_id on each include call and on each value reference. No dependency facts, because Chart.yaml declares no dependencies. Still no I/O.
3The codeanalyzer_iac_config facet on .codeanalyzer-iac.yaml with the base and no-service-account profiles. A render for each profile: 16 resources for base and 15 for no-service-account. The kubernetes_resource_addresses map. Still no cluster access.

The render examples and the Cypher examples need level 3. The other jq examples also work on a level 1 document.

Section titled “Inventory: files, charts, roles”

Cypher examples need the graph

Each Cypher query reads the graph that the Publish to Neo4j section writes. If you want to run a Cypher example, publish the graph first.

Section titled “List the Helm files and their roles”

Every file gets an Artifact. A file that Helm owns also gets an iac facet with a kind and, for most kinds, a list of roles.

This Cypher query returns the same inventory.

The chart facet carries the fields of Chart.yaml.

Templates: helpers, includes, values

Section titled “Templates: helpers, includes, values”

Count the includes of each named template

Section titled “Count the includes of each named template”

_helpers.tpl defines six named templates. The template files call them with include. Four of the nine calls are inside _helpers.tpl itself. At level 2 and higher, each call carries the target_id of its definition.

The jq form counts the calls without the graph.

Find the values keys that no template reads

Section titled “Find the values keys that no template reads”

The IAC_REFERENCES_VALUE edges are level 2 facts, and the graph always holds level 3. Every key in values.yaml is a ConfigKey with the HelmValue label, parent keys included. A key that no IAC_REFERENCES_VALUE edge points at is never read.

Find where serviceAccount.create is read

Section titled “Find where serviceAccount.create is read”

Each value reference records a path_expression without the .Values. prefix.

At level 2 and higher, each of these references also has a target_id that names the key serviceAccount.create in values.yaml.

Count the resource documents each template can emit

Section titled “Count the resource documents each template can emit”

Each YAML document in a template file becomes one resource_templates entry. This is a source fact, so serviceaccount.yaml counts 1 whatever a render profile sets.

Renders: profiles and Kubernetes resources

Section titled “Renders: profiles and Kubernetes resources”

At level 3 the chart facet holds three renders. Two renders come from the configured profiles. The third comes from the default profile that the backend adds to every chart. The jq examples filter by profile_id and the Cypher examples filter by profile name, so the default render adds no rows.

List everything the base profile renders

Section titled “List everything the base profile renders”

Each succeeded render owns its KubernetesResource nodes through IAC_PRODUCES.

The jq form counts the resources of the base render by kind.

Compare no-service-account with base

Section titled “Compare no-service-account with base”

The no-service-account profile renders 15 resources, one fewer than base. The ServiceAccount is the resource that the empty serviceAccount.create removes.

Find Deployments with no Service of the same name

Section titled “Find Deployments with no Service of the same name”

The Deployment at templates/deployment.yaml:238 has the name quarkuscoffeshop-web. The Service at templates/service.yaml:120 has the name quarkuscoffeeshop-web, with one more e. The backend records each name exactly as written, so a name comparison finds the difference.

The jq form subtracts the Service names from the Deployment names.

The first row is a different mismatch. The Deployment quarkuscoffeeshop-counter has no Service of that name, and the Service quarkuscoffeeshop-core has no Deployment of that name.

Find rendered resources with source provenance

Section titled “Find rendered resources with source provenance”

A resource gets an IAC_DERIVED_FROM edge only when its template file holds exactly one resource document. deployment.yaml and service.yaml hold seven documents each, so their resources have no such edge.

Find the Helm hooks

Section titled “Find the Helm hooks”

A rendered resource keeps its annotations. The test Pod is the only resource with a helm.sh/hook annotation.

Publish to Neo4j

Section titled “Publish to Neo4j”

Write the graph, then analyze from the graph

Section titled “Write the graph, then analyze from the graph”

--emit neo4j raises the level to 3 and writes the graph over Bolt. It puts nothing on stdout. A positional Neo4j URI switches caniac to graph mode. In graph mode the backend reads each Artifact.source from the graph, makes sure that each sha256 matches, and writes the same row set. The at-scale guide describes the shared Neo4j workflow.
