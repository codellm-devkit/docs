<Aside type="caution" title="Stub: planned">
The Go SDK does not exist yet. This page tracks intent and design so the work has a home. For a working SDK today, use the [Python SDK](/reference/python-api/) (the experimental [TypeScript SDK](https://github.com/codellm-devkit/typescript-sdk) is also live).
</Aside>

A **Go SDK** is a planned CLDK *frontend*: an idiomatic Go API over the canonical analysis JSON that the [codeanalyzer backends](/backends/) produce. Because the backends do all the language analysis, a Go frontend inherits **every** backend for free, the same call graphs, symbol tables, and reachability available to the Python SDK.

## What it will provide

- `cldk.New(language, projectPath)` style construction returning an `Analysis` handle.
- The core methods the [Python SDK](/reference/python-api/) exposes (`GetSymbolTable`, `GetCallGraph`, `GetCallers`, `GetCallees`, …) over the same typed models.
- Read-only consumption of the canonical `analysis.json`, so it stays in lockstep with every backend.

## Status

On the roadmap, not started. The [Python SDK](/reference/python-api/) is the reference implementation; see [Add a Rust frontend](/contributing/rust-frontend/) for how a second native frontend is structured, the same shape applies to Go.

<Aside type="tip" title="Adding a language pack">
CLDK ships a skill that scaffolds first-class support for a new language end to end (a `codeanalyzer-<lang>` backend plus the SDK bindings). See [codellm-devkit/developer-skillset](https://github.com/codellm-devkit/developer-skillset).
</Aside>
